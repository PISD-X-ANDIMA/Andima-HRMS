|---|---|
| Status | Draft, belum dipublikasikan ke Docmost |

| Terkait | TR-12/13 (otorisasi), TR-14 (aktor & waktu), TR-16 (RLS), TR-17 (error aman), TR-19 (validasi server) |

## 1. Struktur

```
app/api/d4/<resource>/route.ts            GET/POST, hanya memanggil handler
app/api/d4/<resource>/[id]/route.ts       GET detail
app/api/d4/<resource>/[id]/versions/…     POST revisi (development, training)
modules/d4/server/_lib/http.ts            envelope, ApiError, validator field.*
modules/d4/server/_lib/session.ts         d4Session, d4Access, requireWriter
modules/d4/server/<resource>/index.ts     handler per resource
modules/d4/web/data/api-source.ts         klien browser yang memanggil /api/d4/*
```

UI tidak lagi memanggil Supabase langsung. Semua baca dan tulis melewati `/api/d4/*`. Mode preview (`NEXT_PUBLIC_D4_DATA_MODE=fixture`, hanya di development) memakai `fixture-source.ts` yang menerapkan aturan yang sama di memori.

## 2. Autentikasi dan izin

- Setiap request memakai cookie sesi Supabase pengguna (`@supabase/ssr`). Tanpa sesi, respons **401 UNAUTHENTICATED**.
- Peran dibaca dari `d3_user_access.app_role` berdasarkan `auth_user_id`.
- **Internal (tulis)**: semua `POST` memanggil `requireWriter()`, sehingga hanya **HR** dan **MANAGER** yang boleh. Peran lain mendapat **403 FORBIDDEN**.
- **Baca**: semua peran yang punya akses. RLS D4 tetap aktif: EMPLOYEE hanya menerima record miliknya sendiri. API tidak memakai service role key.
- **Cakupan tim MANAGER**: UI (`visibleEmployees`/`assessableEmployees`) dan sumber data lokal (fixture/demo) membatasi MANAGER pada employee di departemennya sendiri, tanpa dirinya. **API live belum** membatasi ini: endpoint menerima `employeeId` mana pun yang lolos RLS, karena data reporting line (atasan langsung) belum tersedia dari D3. Setelah D3 menyediakannya, scoping perlu ditambahkan di `requireWriter()`/handler dan di RLS, bukan hanya di UI.
- Penilaian, development requirement, dan training untuk **diri sendiri** ditolak (422) baik di API maupun sumber lokal.
- Kolom aktor (`actor_auth_user_id`, `actor_employee_id`) dan `created_at` diisi default database dari sesi, bukan dari body request (TR-14).

## 3. Format respons

Sukses:

```json
{ "data": { "...": "..." } }
```

Gagal:

```json
{ "error": { "code": "VALIDATION_FAILED", "message": "Field period harus berformat YYYY-MM." } }
```

| Code | HTTP | Kapan |
|---|---|---|
| `BAD_REQUEST` | 400 | Body bukan objek JSON |
| `UNAUTHENTICATED` | 401 | Tidak ada sesi login |
| `FORBIDDEN` | 403 | Peran tidak boleh menulis, atau RLS menolak |
| `NOT_FOUND` | 404 | Record tidak ada atau tidak terlihat oleh akun |
| `METHOD_NOT_ALLOWED` | 405 | Method HTTP tidak didukung route ini (header `Allow` berisi method yang didukung) |
| `CONFLICT` | 409 | Submit ganda atau bersamaan untuk record yang sama (unique violation `23505`, atau snapshot kompetensi yang sudah ada) |
| `VALIDATION_FAILED` | 422 | Field tidak valid atau aturan bisnis dilanggar |
| `INTEGRATION_ERROR` | 503 | Supabase atau layanan hulu tidak dapat dihubungi (`fetch failed`, `ECONNREFUSED`, timeout). Pesan generik, detail dicatat di log server |
| `CONFIGURATION_ERROR` | 503 | Env Supabase server belum lengkap. Pesan "Konfigurasi server belum lengkap.", dicatat sekali di log tanpa stack |
| `SERVER_ERROR` | 500 | Selain di atas. Pesan dibuat generik; detail SQL dan stack trace hanya dicatat di log server |

Kode tambahan yang dibuat **klien** (`modules/d4/web/data/api-source.ts`) bila tidak ada respons berformat D4:

| Code | Status | Kapan | Pesan ke user |
|---|---|---|---|
| `NETWORK_ERROR` | 0 | `fetch` gagal total (offline, DNS) | "Tidak dapat terhubung ke server. Periksa koneksi internet lalu coba lagi." |
| `TIMEOUT` | 0 | Tidak ada respons dalam 20 detik | "Server terlalu lama merespons. Coba lagi beberapa saat lagi." |
| `INTEGRATION_ERROR` | 502/503/504 | Gateway/proxy menjawab tanpa envelope D4 | "Layanan data HRMS sedang tidak dapat dihubungi. Coba lagi beberapa saat lagi." |

Bila simpan berhasil tetapi muat ulang data gagal, UI tetap menganggap simpan **berhasil** dan meminta user memuat ulang halaman, supaya record tidak tersimpan dua kali.

`POST` yang berhasil mengembalikan **201** dengan `{ "data": { "id": "<uuid>" } }`.

## 4. Endpoint

Filter `?employee_id=<uuid>` tersedia pada semua endpoint daftar.

| Method | Path | Handler | Keterangan |

| GET | `/api/d4/snapshot` | `snapshot.getSnapshot` | Semua data D4 yang boleh dilihat akun (dipakai UI) |
| GET | `/api/d4/kpi-catalog?role_order=` | `kpi-catalog.getCatalog` | Katalog KPI aktif untuk form KPI Scorecard (V5.1 bila sudah dimigrasi, selain itu versi terbaru di DB) |
| GET, POST | `/api/d4/performance-evaluations` | `listEvaluations`, `createEvaluation` | FR-D4-001 |
| GET | `/api/d4/performance-evaluations/:id` | `getEvaluation` | |
| GET, POST | `/api/d4/kpi-assessments` | `listAssessments`, `createAssessment` | FR-D4-002 |
| GET | `/api/d4/kpi-assessments/:id` | `getAssessment` | |
| GET, POST | `/api/d4/competency-assessments` | `listCompetency`, `createCompetency` | FR-D4-003 |
| GET, POST | `/api/d4/development-needs` | `listDevelopment`, `createDevelopment` | FR-D4-004 |

## 5. Body POST dan aturan server

### Status error POST

Semua skor (`overallScore` di performance-evaluations, `raw_score` di kpi-assessments) adalah **bilangan bulat 1–5**. Kolom "Sekarang" berlaku mulai branch `feature/D4-week5-fixes`; kolom "Baseline `bcb92d8`" untuk perbandingan.

| Kondisi | Baseline `bcb92d8` | Sekarang |
|---|---|---|
| Skor bukan bilangan bulat (mis. `3.5`) atau di luar 1–5 | 422 `VALIDATION_FAILED` (performance: ditolak saat repository memvalidasi) | 422 `VALIDATION_FAILED`, dicek langsung di handler |
| `employeeId` tidak ada di data employee | 422 `VALIDATION_FAILED` (KPI: "Employee tidak ditemukan"; performance: "Posisi employee tidak tersedia") | **404** `NOT_FOUND` |
| Submit ganda atau bersamaan untuk record yang sama (unique violation database `23505`) | 500 `SERVER_ERROR` | **409** `CONFLICT` |
| Konfigurasi server tidak lengkap (`NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` kosong) | 500 `SERVER_ERROR` | **503** `CONFIGURATION_ERROR` |
| Trigger database menolak data (`raise exception`, kode Postgres `P0001`, mis. bobot KPI tidak sesuai katalog) | 500 `SERVER_ERROR` | 422 `VALIDATION_FAILED` dengan pesan dari trigger |
| Snapshot kompetensi identik dikirim ulang di hari yang sama (klik ganda) | tersimpan dua kali | 201 dengan id snapshot yang sudah ada (tidak ada baris baru) |
| Periode yang sudah punya record tanpa `revisionOf` yang benar | 422 `VALIDATION_FAILED` | 422 `VALIDATION_FAILED` |
| Akun HR/MANAGER tanpa `employee_id` di `d3_user_access` | 403 `FORBIDDEN` pada performance-evaluations dan kpi-assessments ("Akun belum terhubung dengan data employee"); `requireWriter()` sendiri hanya memeriksa peran, sehingga POST lain tetap lolos | sama (belum diubah) |

Pemeriksaan sesi dan peran (401, 403 untuk EMPLOYEE, akun tanpa baris akses, dan akun tanpa `employee_id`) diuji di `tests/d4/api.test.ts` dengan `requireWriter()` asli di atas klien Supabase tiruan.

### performance-evaluations

| Field | Tipe | Aturan |
|---|---|---|
| `employeeId` | uuid | wajib |
| `period` | `YYYY-MM` | wajib |
| `status` | `completed` | wajib; FR-D4-001 tidak mendefinisikan evaluasi draft |
| `evaluationDate` | `YYYY-MM-DD` | wajib |
| `evaluator` | — | **diabaikan**; server memakai nama employee milik akun yang login (`d3_user_access.employee_id`) |
| `revisionOf` | uuid | wajib bila sudah ada evaluasi untuk employee + periode ini: id evaluasi terbaru periode itu; selain itu 422 `VALIDATION_FAILED` |
| `overallScore` | bilangan 1–5 (Hasil evaluasi) | wajib, dipilih manual oleh evaluator |
| `generalNotes` | teks ≤4000 | wajib (catatan evaluasi) |
| `evidenceReference` | teks ≤500 | opsional |

`employeeId` tidak boleh sama dengan employee milik akun yang login (tidak menilai diri sendiri).

Kolom lama `review_status` dan `aspects` di tabel `d4_performance_evaluations` tidak ada di FR-D4-001, sehingga tidak diterima dari klien. API mengisinya dengan nilai netral (`Needs Review`, `[]`) agar skema tidak perlu diubah.

### kpi-assessments

| Field | Tipe | Aturan |
|---|---|---|
| `employeeId`, `period`, `status` | | seperti di atas |
| `roleOrder` | 1–10 | harus sama dengan KPI jabatan hasil pemetaan position employee (server menolak bila berbeda), dan harus punya tepat 5 indikator dengan total bobot 100 |
| `lines` | 5 × `{ kpi_name, target, actual, raw_score, comment }` | urutan dan `kpi_name` harus sama dengan katalog; `raw_score` bilangan bulat 1–5, wajib bila `completed` |
| `evaluationDate` | | wajib bila `completed` |
| `evaluatorName` | | **diabaikan**; diisi nama akun yang login. `employeeId` tidak boleh diri sendiri |
| `revisionOf` | uuid | seperti performance-evaluations: wajib bila scorecard periode itu sudah ada |

Bobot selalu diambil dari katalog server, bukan dari body. Skor terbobot = bobot × skor mentah, dan total = Σ skor terbobot, yang dihitung trigger database `d4_calculate_kpi_assessment`. Tidak ada konversi realisasi → skor dan tidak ada label tercapai.

### competency-assessments

`employeeId`, `positionId`, `effectiveDate`. Gap dihitung ulang di server dari `position_requirements` dan `d3_employee_skills`, tidak diterima dari klien. Skill tanpa bukti menghasilkan `Bukti Belum Cukup` (ditampilkan "Data Belum Cukup"), bukan `Gap`.

### development-needs

| Field | Aturan |
|---|---|
| `employeeId` | uuid |
| `sourceType` | `competency_gap` \| `role_change` \| `performance_context` |
| `sourceRef` | uuid record sumber: requirement yang berstatus Gap, competency assessment `role-change`, atau evaluasi `completed`, **milik employee yang sama** |
| `objective` | wajib, ≤500 |
| `priority` | `High` \| `Medium` \| `Low` |
| `notes` | opsional |

Untuk `competency_gap`, sumber yang masih punya requirement belum Completed ditolak (satu requirement terbuka per gap). Dibuat lewat RPC `d4_create_development_need` (need + revisi 1 dalam satu transaksi). `POST …/:id/versions` body: `{ status: Identified|Planned|In Progress|Completed, notes }`.

### training-records

| Field | Aturan |
|---|---|
| `employeeId`, `developmentNeedId` | need harus milik employee yang sama dan **belum Completed** |
| `activity` | wajib, ≤200 |
| `date` | `YYYY-MM-DD` |
| `status` | `Planned` \| `In Progress` \| `Completed` \| `Cancelled` |
| `result` | wajib bila `Completed` |
| `notes` | opsional |

`POST …/:id/versions` body: `{ status, result, notes }`. Status mundur (mis. Completed → In Progress) atau membuka kembali training Cancelled mewajibkan `notes` sebagai alasan. Training Completed **tidak** mengubah competency gap.

## 6. Contoh

```bash
curl -X POST http://localhost:3000/api/d4/development-needs \
  -H "Content-Type: application/json" \
  --cookie "<cookie sesi supabase>" \
  -d '{"employeeId":"<uuid>","sourceType":"performance_context","sourceRef":"<evaluation-uuid>","objective":"Perkuat ketelitian dokumen","priority":"Medium","notes":""}'
```

## 7. Data demo (seeder)

`npm run seed:d4` (dry run) lalu `npm run seed:d4 -- --apply`. Seeder login sebagai `D4_SEED_EMAIL` (akun HR/MANAGER) dari `.env.local` dan menulis lewat tabel dan RPC yang sama dengan API, sehingga RLS dan trigger tetap berlaku. Setiap baris diberi penanda `[seed-d4]`, dan employee yang sudah punya baris bertanda dilewati. Seeder tidak mengubah atau menghapus data.
