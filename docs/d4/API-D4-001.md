|---|---|
| Status | Draft, belum dipublikasikan ke Docmost |

## 1. Struktur

```
app/api/d4/<resource>/route.ts            GET/POST, hanya memanggil handler
app/api/d4/<resource>/[id]/route.ts       GET detail
app/api/d4/<resource>/[id]/versions/…     POST revisi (development, training)
modules/d4/server/_lib/http.ts            envelope, ApiError, validator field.*
modules/d4/server/_lib/session.ts         d4Session, d4Access, requireWriter
modules/d4/server/<resource>/index.ts     handler per resource
modules/d4/web/data/api-source.ts         klien browser yang memanggil /api/d4/*
```

UI tidak lagi memanggil Supabase langsung. Semua baca dan tulis melewati `/api/d4/*`. Mode preview (`NEXT_PUBLIC_D4_DATA_MODE=fixture`, hanya di development) memakai `fixture-source.ts` yang menerapkan aturan yang sama di memori.

## 2. Autentikasi dan izin

- Setiap request memakai cookie sesi Supabase pengguna (`@supabase/ssr`). Tanpa sesi, respons **401 UNAUTHENTICATED**.
- Peran dibaca dari `d3_user_access.app_role` berdasarkan `auth_user_id`.
- **Internal (tulis)**: semua `POST` memanggil `requireWriter()`, sehingga hanya **HR** dan **MANAGER** yang boleh. Peran lain mendapat **403 FORBIDDEN**.
- **Baca**: semua peran yang punya akses. RLS D4 tetap aktif: EMPLOYEE hanya menerima record miliknya sendiri. API tidak memakai service role key.
- Kolom aktor (`actor_auth_user_id`, `actor_employee_id`) dan `created_at` diisi default database dari sesi, bukan dari body request (TR-14).

## 3. Format respons

Sukses:

```json
{ "data": { "...": "..." } }
```

Gagal:

```json
{ "error": { "code": "VALIDATION_FAILED", "message": "Field period harus berformat YYYY-MM." } }
```

| Code | HTTP | Kapan |
|---|---|---|
| `BAD_REQUEST` | 400 | Body bukan objek JSON |
| `UNAUTHENTICATED` | 401 | Tidak ada sesi login |
| `FORBIDDEN` | 403 | Peran tidak boleh menulis, atau RLS menolak |
| `NOT_FOUND` | 404 | Record tidak ada atau tidak terlihat oleh akun |
| `METHOD_NOT_ALLOWED` | 405 | Method HTTP tidak didukung route ini (header `Allow` berisi method yang didukung) |
| `CONFLICT` | 409 | Submit ganda atau bersamaan untuk record yang sama (unique violation `23505`, atau snapshot kompetensi yang sudah ada) |
| `VALIDATION_FAILED` | 422 | Field tidak valid atau aturan bisnis dilanggar |
| `INTEGRATION_ERROR` | 503 | Supabase atau layanan hulu tidak dapat dihubungi (`fetch failed`, `ECONNREFUSED`, timeout). Pesan generik, detail dicatat di log server |
| `CONFIGURATION_ERROR` | 503 | Env Supabase server belum lengkap. Pesan "Konfigurasi server belum lengkap.", dicatat sekali di log tanpa stack |
| `SERVER_ERROR` | 500 | Selain di atas. Pesan dibuat generik; detail SQL dan stack trace hanya dicatat di log server |

Kode tambahan yang dibuat **klien** (`modules/d4/web/data/api-source.ts`) bila tidak ada respons berformat D4:

| Code | Status | Kapan | Pesan ke user |
|---|---|---|---|
| `NETWORK_ERROR` | 0 | `fetch` gagal total (offline, DNS) | "Tidak dapat terhubung ke server. Periksa koneksi internet lalu coba lagi." |
| `TIMEOUT` | 0 | Tidak ada respons dalam 20 detik | "Server terlalu lama merespons. Coba lagi beberapa saat lagi." |
| `INTEGRATION_ERROR` | 502/503/504 | Gateway/proxy menjawab tanpa envelope D4 | "Layanan data HRMS sedang tidak dapat dihubungi. Coba lagi beberapa saat lagi." |

Bila simpan berhasil tetapi muat ulang data gagal, UI tetap menganggap simpan **berhasil** dan meminta user memuat ulang halaman, supaya record tidak tersimpan dua kali.

`POST` yang berhasil mengembalikan **201** dengan `{ "data": { "id": "<uuid>" } }`.

## 5. Body POST dan aturan server

### Status error POST

Semua skor (`overallScore` di performance-evaluations, `raw_score` di kpi-assessments) adalah **bilangan bulat 1–5**, kecuali `raw_score` untuk katalog V6 (periode mulai 2026-11): **1–100**. Kolom "Sekarang" berlaku mulai branch `feature/D4-week5-fixes`; kolom "Baseline `bcb92d8`" untuk perbandingan.

| Kondisi | Baseline `bcb92d8` | Sekarang |
|---|---|---|
| Skor bukan bilangan bulat (mis. `3.5`) atau di luar skala katalognya (1–5 untuk V3.1/V5.1, 1–100 untuk V6) | 422 `VALIDATION_FAILED` (performance: ditolak saat repository memvalidasi) | 422 `VALIDATION_FAILED`, dicek langsung di handler |
| `employeeId` tidak ada di data employee | 422 `VALIDATION_FAILED` (KPI: "Employee tidak ditemukan"; performance: "Posisi employee tidak tersedia") | **404** `NOT_FOUND` |
| Submit ganda atau bersamaan untuk record yang sama (unique violation database `23505`) | 500 `SERVER_ERROR` | **409** `CONFLICT` |
| Konfigurasi server tidak lengkap (`NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` kosong) | 500 `SERVER_ERROR` | **503** `CONFIGURATION_ERROR` |
| Trigger database menolak data (`raise exception`, kode Postgres `P0001`, mis. bobot KPI tidak sesuai katalog) | 500 `SERVER_ERROR` | 422 `VALIDATION_FAILED` dengan pesan dari trigger |
| Snapshot kompetensi identik dikirim ulang di hari yang sama (klik ganda) | tersimpan dua kali | 201 dengan id snapshot yang sudah ada (tidak ada baris baru) |
| Periode yang sudah punya record tanpa `revisionOf` yang benar | 422 `VALIDATION_FAILED` | 422 `VALIDATION_FAILED` |
| Akun HR/MANAGER tanpa `employee_id` di `d3_user_access` | 403 `FORBIDDEN` pada performance-evaluations dan kpi-assessments ("Akun belum terhubung dengan data employee"); `requireWriter()` sendiri hanya memeriksa peran, sehingga POST lain tetap lolos | sama (belum diubah) |

Pemeriksaan sesi dan peran (401, 403 untuk EMPLOYEE, akun tanpa baris akses, dan akun tanpa `employee_id`) diuji di `tests/d4/api.test.ts` dengan `requireWriter()` asli di atas klien Supabase tiruan.

### Periode terbuka dan tertutup (24 Nov 2026)

Berlaku untuk POST `kpi-assessments` dan `performance-evaluations` (review dosen 24 Nov 2026: periode dibuka dan ditutup, bukan dipilih bebas).

- Terbuka: bulan berjalan dan bulan sebelumnya (WIB). Oktober tertutup pada 1 Desember 00.00 WIB.
- Periode yang lebih lama terbuka selama HR membukanya kembali di `d4_period_reopenings` sampai `open_until` (termasuk hari itu). Baris terbaru suatu periode yang berlaku, jadi baris dengan `open_until` lebih awal menutupnya lagi.
- Tidak ada periode sebelum `2026-09`.
- Ditolak dengan 422 `VALIDATION_FAILED`, sebelum aturan revisi:
  - periode yang belum dimulai: `Period belum dimulai. Performance Review hanya untuk periode yang sudah berjalan.`
  - periode yang ditutup: `Periode ini sudah ditutup. Penilaian hanya bisa disimpan di periode yang terbuka; HR dapat membuka kembali periode lama.`
  - periode sebelum September 2026: `Penilaian D4 dimulai dari periode September 2026.`
- Snapshot (`GET /api/d4/snapshot`) memuat `periodReopenings: { period, openUntil, reason, createdAt }[]`. Selama tabel belum ada (PGRST205), isinya kosong dan aturan default berlaku.
- Setelah migrasi `20261124150000_d4_period_reopenings.sql`, trigger database memegang aturan yang sama dan mengisi `evaluation_date` dengan hari ini untuk insert langsung lewat PostgREST.
- `POST /api/d4/period-reopenings` `{ period, openUntil, reason }`: HR saja (403 untuk peran lain). `period` dari `2026-09` sampai dua bulan lalu (bulan ini dan bulan lalu sudah terbuka), `openUntil` tidak sebelum awal periode, `reason` 5–500 karakter; selain itu 422. Sebelum migrasi: 503 `CONFIGURATION_ERROR`.

### kpi-assessments

| Field | Tipe | Aturan |
|---|---|---|
| `employeeId`, `period`, `status` | | seperti di atas |
| `roleOrder` | 1–10 (katalog D4) atau 1000 + nomor job code D1 (JP011 → 1011) | harus sama dengan KPI jabatan hasil pemetaan position employee (server menolak bila berbeda), dan set KPI-nya harus punya minimal 1 indikator dengan total bobot 100 |
| `lines` | N × `{ kpi_name, target, actual, raw_score, comment }`, N = jumlah KPI posisi di katalog | urutan dan bobot mengikuti katalog; `kpi_name` wajib dan boleh diubah (≤200); `raw_score` = angka Actual di form (Q4, 20 Okt 2026), bilangan bulat 1–5 (V3.1/V5.1) atau 1–100 (V6), wajib bila `completed`; `actual` teks ≤200 disimpan apa adanya (form mengirim angka yang sama dengan `raw_score`; teks lain dari klien lama tampil sebagai realisasi di Comment); `target` diabaikan, server memakai target katalog (85 bila katalog kosong) |
| `evaluationDate` | | **diabaikan** sejak 24 Nov 2026: server menyimpan tanggal hari penyimpanan (WIB), jadi penilaian tidak bisa dicatat mundur |
| `evaluatorName` | | **diabaikan**; diisi nama akun yang login. `employeeId` tidak boleh diri sendiri |
| `revisionOf` | uuid | seperti performance-evaluations: wajib bila scorecard periode itu sudah ada |
| `generalNotes` | teks ≤4000 | wajib (Notes) |
| `evidenceReference` | teks ≤500 | wajib (Reference): kosong, spasi, `null`, atau tidak dikirim → 422 `Reference wajib diisi.`. DB ikut menolak setelah migrasi `20261020120000_d4_kpi_reference_required.sql` diterapkan |

Bobot selalu diambil dari katalog server, bukan dari body. Skor terbobot = bobot × skor (bobot 20% × skor 90 = 18), dan total = Σ skor terbobot, yang dihitung trigger database `d4_calculate_kpi_assessment`. Skor adalah angka Actual yang diisi penilai; tidak ada konversi lain dari realisasi dan tidak ada label tercapai. Kategori performa (di bawah 80 Under, 80–85 Average, di atas 85 High) dihitung di UI dari total scorecard V6 saja, tidak disimpan dan tidak dikirim API.

### kpi-daily

Satu-satunya POST yang **tidak** dibatasi ke HR/MANAGER: setiap akun yang terhubung ke data pegawai mengisi skornya sendiri, termasuk `MANAGEMENT` (Director). Contoh klien 14 Okt 00:33:23 adalah seorang direktur yang menilai KPI-nya sendiri; untuk data lain MANAGEMENT tetap read-only. Pegawai, KPI jabatan, dan indikator diambil dari sesi dan katalog periode, tidak dari body. `employeeId` dan `roleOrder` di body diabaikan.

| Field | Tipe | Aturan |
|---|---|---|
| `entryDate` | YYYY-MM-DD | wajib; hari ini atau hari sebelumnya di periode WIB berjalan |
| `lines` | N × `{ raw_score, comment }`, N = jumlah KPI posisi di katalog | urutan katalog; `raw_score` bilangan bulat 1–5 (V5.1) atau 1–100 (V6), wajib; `comment` ≤500, opsional |

Posisi tanpa KPI di katalog → 422. Sebelum migrasi `20261108130000_d4_kpi_daily_entries.sql` diterapkan, POST menjawab 503 `CONFIGURATION_ERROR` dan snapshot tidak memuat `kpiDaily`. Menyimpan lagi tanggal yang sama mencatat koreksi; entri terbaru per tanggal yang dihitung.

### competency-assessments

`employeeId`, `positionId`, `effectiveDate`, dan `assessedWith` opsional (≤200, nama/jabatan atasan atau departemen yang menilai bersama HR; kolom `assessed_with` dari migrasi `20261019120000`). Gap dihitung ulang di server dari `position_requirements` dan `d3_employee_skills`, tidak diterima dari klien. Skill tanpa bukti menghasilkan `Bukti Belum Cukup` (ditampilkan "Data Belum Cukup"), bukan `Gap`.

### development-needs

| Field | Aturan |
|---|---|
| `employeeId` | uuid |
| `sourceType` | `competency_gap` \| `role_change` \| `performance_context` |
| `sourceRef` | uuid record sumber: requirement yang berstatus Gap, competency assessment `role-change`, atau evaluasi `completed`, **milik employee yang sama** |
| `objective` | wajib, ≤500 |
| `priority` | `High` \| `Medium` \| `Low` |
| `method`, `pic` | opsional, ≤120 |
| `notes` | opsional |

Untuk `competency_gap`, sumber yang masih punya requirement belum Completed ditolak (satu requirement terbuka per gap). Dibuat lewat RPC `d4_create_development_need` (need + revisi 1 dalam satu transaksi). `POST …/:id/versions` body: `{ status: Identified|Planned|In Progress|Completed, notes, priority?, method?, pic?, reassessment? }`. Field detail yang tidak dikirim (atau `null`) tetap; `""` mengosongkan `method`/`pic`. Revisi tanpa perubahan status wajib mengubah salah satu detail atau mencatat keputusan baru. `reassessment` hanya untuk requirement yang Completed: `Retraining` membuka kembali requirement dengan status `Planned` (keputusan itu menjadi alasannya, jadi `notes` tidak wajib; ditolak bila sudah ada requirement terbuka lain untuk gap yang sama), `Meets requirement` tetap `Completed`. Keputusan yang sama dengan yang sudah berlaku ditolak. Setelah Retraining, menyelesaikan requirement lagi hanya menghitung training Passed yang dicatat sesudahnya; tanpa itu `notes` wajib. Kolom `priority`, `method`, `pic`, `reassessment` di `d4_development_need_versions` datang dari migrasi `20261019120000_d4_development_edit_reassessment.sql`; baris revisi hanya menyimpan detail yang berubah.

### training-records

| Field | Aturan |
|---|---|
| `employeeId`, `developmentNeedId` | need harus milik employee yang sama dan **belum Completed** |
| `activity` | wajib, ≤200 |
| `date` | `YYYY-MM-DD` |
| `status` | `Planned` \| `In Progress` \| `Completed` \| `Cancelled` |
| `result` | wajib bila `Completed` |
| `notes` | opsional |

`POST …/:id/versions` body: `{ status, result, notes }`. Status mundur (mis. Completed → In Progress) atau membuka kembali training Cancelled mewajibkan `notes` sebagai alasan. Training Completed **tidak** mengubah competency gap.

`POST …/bulk` body: `{ items: [...] }`. Setiap baris punya `op`:
- `create`: field yang sama dengan `POST /training-records`;
- `version`: `trainingId`, lalu field `…/:id/versions`;
- `complete`: `trainingId`, lalu field `…/:id/complete`.

Aturan setiap baris sama dengan endpoint satuannya. Baris diproses berurutan, dan baris yang ditolak tidak menghentikan baris lain. Jawaban 200 berisi `{ ok: true }` atau `{ ok: false, message }` per baris. Login dan snapshot dimuat sekali per permintaan. Snapshot dimuat ulang hanya sebelum baris `complete` milik pegawai yang sudah ditulis baris sebelumnya. Layar mengirim 10 baris per permintaan, dengan batas waktu 60 detik.

## 7. Data demo (seeder)

`npm run seed:d4` (dry run) lalu `npm run seed:d4 -- --apply`. Seeder login sebagai `D4_SEED_EMAIL` (akun HR/MANAGER) dari `.env.local` dan menulis lewat tabel dan RPC yang sama dengan API, sehingga RLS dan trigger tetap berlaku. ## 8. KPI dari D1 dan view skor untuk D1 (24 Nov 2026)

Migrasi `20261124130000_d4_kpi_from_d1.sql` (diterapkan di production 24 Nov 2026).

**Katalog.** Mulai periode 2026-11, posisi D3 yang dipetakan D1 lewat `d3_d1_position_mappings` memakai KPI dari `d1_kpi_definitions`. Syaratnya: posisi D1 `Active`, KPI aktif dan tidak dihapus, dan total bobotnya 100. Jumlah KPI mengikuti D1. Posisi yang belum dipetakan tetap memakai peran katalog D4 V6. Aplikasi membaca view `d4_kpi_catalog_rows` dan `d4_kpi_position_roles` (kolom tambahan `kpi_source` `D1`/`D4` dan `d1_job_code`). Selama migrasi belum diterapkan, view itu belum ada (PGRST205) dan aplikasi kembali membaca tabel `d4_kpi_role_catalog` dan `d4_position_kpi_roles`.

**Baris tersimpan.** Trigger `d4_calculate_kpi_assessment` menambahkan `d1_kpi_id` ke setiap baris scorecard dan Daily KPI yang memakai KPI D1, sehingga skor tetap tertaut ke definisinya walau nama KPI diubah di form atau di D1.

**View `d4_kpi_scores_for_d1`.** Satu baris per KPI per entri. Semua kolom `d1_kpi_scores` ada dengan nama dan tipe yang sama, jadi D1 cukup mengganti nama tabel `d1_kpi_scores_dummy`. Kolom tambahan ditandai *(D4)*:

| Kolom | Isi |
|---|---|
| `id` | uuid tetap per baris KPI (dari id entri D4 dan id KPI D1) |
| `source` *(D4)* | `daily` (entri terbaru per pegawai dan tanggal) atau `period` (Performance Review `completed` terbaru per pegawai dan periode) |
| `employee_ref`, `employee_name`, `employment_status` | dari `b2_register` |
| `position_id`, `kpi_id` | posisi dan KPI di D1 (`d1_kpi_definitions`). Baris lama tanpa `d1_kpi_id` dicocokkan lewat nama KPI di posisi D1 yang dipetakan; yang tidak cocok tidak ditampilkan |
| `score` | skor 1–100 KPI itu |
| `period`, `entry_date` *(D4)* | tanggal pertama periode; tanggal entri untuk `daily` |
| `overall_score`, `status` *(D4)* | total entri dan kategori `High` (di atas 85), `Average` (80–85), `Under` (di bawah 80) |
| `note`, `created_at`, `d4_record_id` *(D4)* | Notes Performance Review, waktu simpan, id entri D4 |

Hanya skala 1–100 (V6 dan sesudahnya). Yang bisa membaca: HR, MANAGER, MANAGEMENT, pemilik data, dan `service_role`. `anon` tidak punya akses. Akun D1 biasa yang login hanya melihat skornya sendiri; untuk membaca semua skor, D1 memakai sesi HR, Manager, atau Management, atau kunci `service_role` di server.
